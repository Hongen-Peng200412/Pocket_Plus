# 源码学习注释规则

## 1. 文档职责

本文规定如何把一段已经完成的实现历史整理为便于个人阅读的学习历史。目标是解释代码、维护学习注释和组织 Git，不是重新开发、审查或验证实现本身。

本文先在 Pocket_Plus 的 Stage1 学习任务中实践。若实践结果稳定，可再提炼为正式 skill；在转正前，agent 仍以 `source-reading-annotation-workflow` 为执行权威。

## 2. 四个术语

- **实现线**：保存真实开发、调试和修复顺序的 Git 历史。
- **学习线**：从同一提交出发，按逻辑依赖重新组织最终正确代码，并增加学习注释的 Git 历史。
- **共同基点**：一轮实现线与学习线共同开始的提交。
- **累计学习分支**：`Learn/model-cumulative`，指向最新完成并接受的学习线终点。

## 3. 双线工作方式

实现线和学习线长期并存，互不改写：

```text
共同基点
├── 实现线：真实实现 → 调试 → 修复 → 最终实现
└── 学习线：按依赖重建最终实现 → 增加注释 → 整理文档
```

学习线不复现已经修复的错误状态。实现线中的修复结果应直接折回它所属的逻辑提交，例如数据修复进入数据提交，数值桥接进入对应推理提交。

学习线完成后，除明确允许的普通注释、Docstring、YAML 注释和学习文档外，代码与配置必须和实现线终点一致。白名单以外的差异属于学习线错误。

下一轮真实实现不直接写在学习分支上，而是从当前 `Learn/model-cumulative` 新建实现分支。该实现结束后，再从相同基点建立新一轮学习线。这样未来实现可以继承已有注释，同时继续保留两种提交历史。

## 4. 工作范围

默认只做以下事项：

1. 回答用户对代码的疑问。
2. 阅读源码并补充学习型注释或 Docstring。
3. 给 YAML 补充不改变配置值的解释。
4. 维护项目学习文档。
5. 创建和整理 Git 学习分支、里程碑与提交。

未经用户另行授权，不运行测试，不 import 项目，不执行 `compileall`、Hydra compose、模型前向、数据 smoke 或服务器任务，也不安装或修改环境。

## 5. 开始前必须确认的边界

每轮开始前至少确认：

1. 共同基点和实现线终点。
2. 哪些差异属于本轮学习范围。
3. 普通注释、Docstring、YAML 注释和学习文档的允许范围。
4. 目标差异之外的既有依赖如何处理：完全不修改，或只补理解当前链所必需的最小注释。
5. 测试文件是否属于用户阅读范围。
6. 学习分支是否推送；默认先本地整理，推送需要单独授权。

## 6. Git 组织

学习线保持一条尽量笔直的提交链。一个里程碑表示一个可独立理解的模块阶段，branch 只作为该阶段最终提交的指针；里程碑内部可以有多笔按依赖排序的提交。

规则如下：

- 第一个提交默认统一清理实现线终点已经删除的文件；删除项不再分散到后续模块提交。
- 第二个提交默认统一冻结测试快照：把实现线终点仍然存在的测试文件按原始 blob 一次性归位。最终已删除的旧测试随第一个删除提交退出；第二个提交之后不再夹带测试变更。
- 后续提交按数据流和模块依赖组织，不照搬实现线的调试时间顺序。
- 生产代码、对应配置和该层学习注释进入同一逻辑提交；测试不跟随各模块重复分层。
- 不保留 `tmp`、`RE`、`fix` 或“补注释”式过程提交。
- 每个里程碑分支指向该模块最后一笔提交。
- `Learn/model-cumulative` 与最新接受的里程碑指向同一提交，不 cherry-pick 出副本。
- 已推送并接受的学习历史不强制改写；后续修订使用新提交或下一轮学习线。

## 7. 注释边界

Python 学习注释同时遵循 `source-reading-annotation-workflow` 与 `code-comment-style-cn`。前者决定学习链应解释哪些数据流和模块关系；后者决定中文 Docstring、变量注释和相关 Markdown 的具体写法。两者都必须满足，不能用模块概述代替函数契约，也不能只写 Docstring 而省略关键变量的类型、shape 和语义。

学习范围内的函数、方法和类默认使用中文多行 Docstring：先写一句用途，再按“输入参数”逐项说明类型、shape/长度和语义，最后写“输出”或“返回值”。只要存在返回值就不得省略返回段；返回 `dict`、`tuple`、`list[dict]`、dataclass 等结构化对象时，必须继续展开每个字段或组成项。无显式参数或无返回值的方法也要写清其状态影响，不能只留一句概述。

数组、张量、列表、字典、mask、索引和中间特征等关键变量使用“类型、当前 shape、简洁语义”的中文注释。当前 shape 使用圆括号，单行 shape 变化使用方括号；只注释能够从当前代码确认的事实，不逐行翻译语法。

参数条目、返回字段、变量说明和普通注释优先保持一条语义一行。不要仅因“原行长度看起来装不下”就轻易换行，也不要把同一个变量的人类可读说明拆到下一行；只有枚举子项、补充独立约束或表达真正的层级关系时才使用续行。

所有坐标、起点、shape、bbox、centroid、voxel index 和 linear index 注释必须明确坐标语义：至少区分世界坐标与体素坐标/索引，并写清 XYZ/ZYX 轴序、连续值或离散整数、corner 或 voxel-center 语义，以及 local/full-map/centered 等所属坐标系。不能只写 shape 后笼统称为“坐标”。

坐标说明至少按以下层次区分，禁止用“坐标”一词代替其中任一层次：

- 世界坐标：连续物理位置，通常为 XYZ 轴序，需写清原点、单位和是否以 BOX 中心为参照。
- voxel 坐标：相对于 voxel 网格的连续位置，需写清 XYZ 轴序、corner 或 voxel-center 语义，以及是 BOX-local 还是 full-map。
- voxel 索引：离散整数网格下标，需写清 XYZ/ZYX 轴序、取整方式和所属网格；`shape` 只表示网格尺寸，不等于坐标值。
- linear index：由明确的 full-map 或 BOX-local ZYX 网格展平得到的离散整数索引，必须写出对应数组和 C-order 轴序。

YAML 使用 `yaml-config-style-cn`：说明消费者、字段类型、语义、特殊值和已经核实的调用链，不猜测未验证行为。

额外约束：

- 保留函数名、字段名、路径和命令等英文技术标识。
- Docstring 可以改写，但不得改变控制流、常量、数据或配置值。
- 测试不属于用户阅读范围时，测试文件只按实现线原样归位，不阅读、不注释、不运行。
- 最终删除的旧文件直接删除，不补注释，也不要求解释其历史。
- 对目标差异之外的既有依赖，必须在行动前询问用户；不得自行扩大注释范围。
- 发现可能的优化点时只写入项目学习文档，不在学习线修改实现。

## 8. 项目学习文档

通用规则与项目知识分开维护：

- 本文只保存可复用规则，不记录本机绝对路径、具体 commit 或项目模块细节。
- 每个项目另设学习文档，记录实际范围、分支、里程碑、代码结构、数据流、字段、shape、阅读边界和留给实现线的事项。

项目学习文档中的改进事项应写明代码位置、现象、证据、可能影响、建议和当前状态。证据不足时明确标记“待确认”，不把推测写成确定缺陷。

## 9. 静态一致性

学习任务不重新证明实现正确性，只检查学习线没有改变实现：

- 用 Git 核对最终文件清单、删除清单和未注释文件的 blob。
- 对允许补注释的 Python 文件，忽略普通注释和 Docstring 后比较剩余结构。
- 对允许补注释的 YAML 文件，忽略注释后比较配置值。
- 不通过运行项目、测试或服务器任务补充这一检查。
