# 测试 pipeline 实施计划

本文记录当前投稿周期内需要实现的测试 pipeline。目标是把深度学习实验和非深度学习 baseline 都纳入同一套“验证集扫阈值、测试集固定评估”的流程，并尽量复用现有推理缓存、后处理、扫参和结果输出逻辑。

## 1. 总体原则

1. `protein_40.json` 是 validation / calibration set，只用于选择 `threshold`。
2. `protein_110.json` 是 held-out test set，只使用 validation 上选出的参数做固定评估，不再扫参。
3. 深度学习实验继续以 `src/inference/main/two_stage_basic.py` 为入口。
4. 深度学习侧直接复用当前活跃配置，不重写 YAML 体系。
5. 非深度学习 baseline 通过过渡脚本生成与深度学习同构的 `.npz` cache，再复用同一套后处理、扫参、评估和输出逻辑。
6. 评估指标集中改在专门评估文件或评估函数中，例如 `src/inference/voxel_evaluator.py`，严格控制改动面。
7. 现有输出惯例继续由 `run_voxel_param_search()` 维护，不在 orchestration 脚本里另造结果目录结构。

现有惯例包括：

```text
best_params.json
best_summary.json
per_sample_best_metrics.json
param_search_results.xlsx
best_outputs/
```

## 2. 深度学习实验

深度学习侧固定为四个模型、两个系统、两个数据集配置：

```text
模型: unet_base / unet_c1 / unet_c2 / emb_unet
系统: stardard / strict
集合: protein_40 / protein_110
```

目前已活跃的 12 个配置：

```text
configs/infer_or_eval/unet_base_stardard_40.yaml
configs/infer_or_eval/unet_base_stardard.yaml
configs/infer_or_eval/unet_base_strict_40.yaml
configs/infer_or_eval/unet_base_strict.yaml
configs/infer_or_eval/unet_c1_stardard_40.yaml
configs/infer_or_eval/unet_c1_stardard.yaml
configs/infer_or_eval/unet_c1_strict_40.yaml
configs/infer_or_eval/unet_c1_strict.yaml
configs/infer_or_eval/unet_c2_stardard_40.yaml
configs/infer_or_eval/unet_c2_stardard.yaml
configs/infer_or_eval/unet_c2_strict_40.yaml
configs/infer_or_eval/unet_c2_strict.yaml
```

未来补齐 `emb_unet` 后，配置总数为 16 个。这些配置相对固定，不作为本轮重构对象。

### 2.1 两个系统

两个系统由配置字段决定：

```text
stardard:
  structure_input_source = cif_gt_path
  sim_map_source = sim_map_path
  gt_receptor_source = cif_gt_path

strict:
  structure_input_source = cif_path
  sim_map_source = sim_map_path_cryoatom
  gt_receptor_source = cif_path
```

后续深度学习与 baseline 都必须保持同一系统内比较，不跨系统混合。

### 2.2 自动化流程

`two_stage_basic.py` 应重构为一套固定自动流程：

```text
输入: 一个 *_40 calibration 配置
自动推断或显式读取对应 protein_110 test 配置

步骤:
  1. 读取 protein_40 配置。
  2. 加载一次模型 checkpoint。
  3. 在 protein_40 上生成或复用深度学习预测缓存。
  4. 在 protein_40 上执行 Stage 1 threshold 粗扫。
  5. 读取 Stage 1 best threshold。
  6. 在 protein_40 上执行 Stage 2 局部 threshold 全量评估。
  7. 读取 Stage 2 best params。
  8. 读取 protein_110 配置。
  9. 在 protein_110 上生成或复用深度学习预测缓存。
  10. 使用 Stage 2 best params 固定评估 protein_110，不再搜索。
```

推荐保留 `--config` 作为 calibration 配置入口，例如：

```bash
python src/inference/main/two_stage_basic.py --config unet_c1_stardard_40
```

对应 test 配置默认由配置名去掉 `_40` 得到，例如：

```text
unet_c1_stardard_40 -> unet_c1_stardard
```

可保留显式覆盖项：

```text
test_config=unet_c1_stardard
```

只用于命名不满足 `_40` 规则的情况。

### 2.3 protein_40 Stage 1

Stage 1 用于从语义分割指标粗略定位合理 threshold，避免一开始被 instance 级指标带向过大的连通域。

固定参数：

```text
filter_strength = basic
min_component_voxels = 10
connectivity_policy = 7_none
merge_dist = 0.0
search_strategy = grid
vis_enable = false
```

搜索空间：

```text
threshold: 0.05 到 1.00，step = 0.01
```

目标函数：

```text
objective_expr = avg_voxel_f1
```

Stage 1 尽量轻量，不做可视化，不把它作为最终报告结果。

### 2.4 protein_40 Stage 2

Stage 2 在 Stage 1 best threshold 周围做局部完整评估，得到最终用于测试集的后处理参数。

固定参数：

```text
filter_strength = basic
min_component_voxels = 10
connectivity_policy = 7_none
merge_dist = 5.0
search_strategy = grid
vis_enable = true
```

搜索空间：

```text
threshold: [stage1_best_threshold - 0.10, stage1_best_threshold + 0.10]
step = 0.01
边界裁剪到 [0.0, 1.0]
```

Stage 2 只搜索 `threshold`，不搜索 `min_component_voxels`、`connectivity_policy`、`merge_dist` 或 advanced 后处理参数。

Stage 2 的目标函数应在评估函数更新后再最终确定。原则上，它应使用最终测试指标中最核心的字段，而不是旧的 per-sample instance average。

### 2.5 protein_110 固定测试

protein_110 阶段不扫参。它读取 protein_40 Stage 2 的 best params，并将这些参数写入当前 test 配置后调用现有 `run_voxel_param_search()`。

为了复用现有输出惯例，test 阶段可以把 `search_space` 置为空：

```text
search_space = {}
```

现有 `optimize_postprocess_params()` 在无 active search space 时会评估一次当前固定参数，并返回同构的 `best_params / best_metrics / history`。因此 test 阶段仍可复用：

```text
best_params.json
best_summary.json
per_sample_best_metrics.json
best_outputs/
```

test 阶段固定：

```text
vis_enable = true
```

## 3. 非深度学习 baseline

非深度学习 baseline 的目标不是另写评估 pipeline，而是生成与深度学习缓存同构的 baseline cache。

### 3.1 baseline family

六组 baseline 固定为：

```text
1. phenix_real_space_diff_map
2. diff_clipnorm_nopost
3. posdiff_clipnorm_DoG1
4. posdiff_clipnorm_DoG2
5. posdiff_clipnorm_smooth1
6. posdiff_clipnorm_smooth2
```

其中 `diff_clipnorm_nopost` 等内部通道名必须使用 `src/datasets/density_channel_builder.py` 中实际支持的命名。

### 3.2 baseline 系统对应关系

baseline 也分 `stardard` 和 `strict` 两个系统，字段来源必须与深度学习配置一致。

内部 density-channel baseline：

```text
stardard:
  structure_input_source = cif_gt_path
  sim_map_source = sim_map_path

strict:
  structure_input_source = cif_path
  sim_map_source = sim_map_path_cryoatom
```

Phenix baseline：

```text
model path = 当前系统 structure_input_source 解析出的结构路径
map path = map_path
```

这样 Phenix baseline 也有 `stardard` 与 `strict` 两套结果。

### 3.3 baseline cache 契约

baseline 过渡脚本输出的 `.npz` 必须尽量复用 `save_voxel_prediction_cache()`，字段与深度学习缓存保持同构：

```text
ligand_pred = baseline_score_map_after_hist_equalization
receptor_pred = None
hardmask = 与当前系统输入结构对应的 hardmask
resampled_emdb = 重采样实验密度图
origin = 重采样网格世界坐标原点
voxel_size = 重采样体素大小
gt_ligand_mask = 与深度学习评估一致的 GT mask
gt_instance_label = 与深度学习评估一致的 GT instance label
gt_ligand_mask_by_class = 若有逐类 GT，则保持一致
gt_instance_label_by_class = 若有逐类 GT，则保持一致
meta = baseline_name / system / score_source / 输入路径等上下文
```

这样 baseline cache 可以进入同一个：

```text
voxel_postprocess.py
voxel_tuning.py
voxel_evaluator.py
run_voxel_param_search()
```

### 3.4 直方图均衡

六组 baseline 都要在额外操作后再进入扫参程序。额外操作是每个样本内部的保序直方图均衡，将 score map 映射到 `[0, 1]`。

定义：

```text
valid_mask = hardmask == 0
score_eq[valid_mask] = rank_percentile(score_raw[valid_mask])
score_eq[hardmask > 0] = 0
```

要求：

```text
1. per-sample 内部完成，不使用 protein_40 全局 CDF。
2. 保序，不能改变体素之间的相对大小顺序。
3. 输出值域为 [0, 1]。
4. 后续 threshold 扫描统一作用在均衡后的 score map 上。
```

### 3.5 baseline 自动化流程

baseline 应采用和深度学习相同的 calibration-test 结构：

```text
对每个 baseline_name 和 system:
  1. 使用 protein_40 配置字段构建 baseline cache。
  2. 在 protein_40 上执行 Stage 1 threshold 粗扫。
  3. 在 protein_40 上执行 Stage 2 threshold 局部完整评估。
  4. 使用 Stage 2 best params。
  5. 使用 protein_110 配置字段构建 baseline cache。
  6. 在 protein_110 上固定评估，不再搜索。
```

过渡脚本只负责：

```text
1. 解析配置和样本 JSON。
2. 生成 baseline score map。
3. 做 per-sample histogram equalization。
4. 写同构 cache。
5. 调用或复用 two_stage_basic 风格的后处理/评估流程。
```

不要复制 `voxel_postprocess.py`、`voxel_tuning.py` 或 `voxel_evaluator.py` 的核心逻辑。

## 4. 评估指标改造

当前旧的 per-sample instance average 不作为主口径继续使用。新评估应围绕 coverage-thresholded one-to-one matching 与 top-K successful ratio。

### 4.1 共同 overlap 逻辑

在 `voxel_evaluator.py` 中抽出公共 helper：

```text
build_instance_overlap_stats(pred_instance_label, gt_instance_label)
```

返回：

```text
pred_ids
gt_ids
pred_sizes
gt_sizes
overlap_count_matrix
pred_cover_matrix
gt_cover_matrix
```

其中：

```text
pred_cover[i, j] = overlap(pred_i, gt_j) / size(pred_i)
gt_cover[i, j] = overlap(pred_i, gt_j) / size(gt_j)
```

valid pair 定义统一为：

```text
valid_pair_t(i, j) =
  pred_cover[i, j] >= t
  AND
  gt_cover[i, j] >= t

t in {0.4, 0.6}
```

instance 级指标和 top-K 指标都必须复用这套 overlap 与 valid-pair 判定。

### 4.2 global instance matching

instance 级评估采用一对一匹配。对每个样本构造 valid-pair score matrix 后，用 Hungarian matching 得到 matched pairs。

推荐匹配分数：

```text
score[i, j] = sqrt(pred_cover[i, j] * gt_cover[i, j])
```

匹配后只保留 `valid_pair_t=True` 的 pair。

全数据集汇总：

```text
global_instance_precision_cov04 = sum(matched_tp_cov04) / sum(num_pred_instances)
global_instance_recall_cov04 = sum(matched_tp_cov04) / sum(num_gt_instances)
global_instance_f1_cov04 = 2PR / (P + R)

global_instance_precision_cov06 = sum(matched_tp_cov06) / sum(num_pred_instances)
global_instance_recall_cov06 = sum(matched_tp_cov06) / sum(num_gt_instances)
global_instance_f1_cov06 = 2PR / (P + R)
```

命名中使用 `global`，不使用 `micro`。

### 4.3 top-K successful ratio

top-K 只接受 per-sample successful ratio，不做 ligand-level recall。

固定：

```text
K = 3, 4, 5
排序字段 = score_mean
```

排序只用 `score_mean`，不引入 `score_max`、`voxel_count` 等回退排序，减少不必要复杂度。

单样本定义：

```text
topK_success_cov04 = 1
  若 score_mean 排名前 K 的任意预测 blob
  与任意 GT instance 构成 valid_pair_0.4
否则为 0

topK_success_cov06 同理使用 valid_pair_0.6
```

全数据集汇总：

```text
top3_success_ratio_cov04 = sum(top3_success_cov04) / num_samples
top4_success_ratio_cov04 = sum(top4_success_cov04) / num_samples
top5_success_ratio_cov04 = sum(top5_success_cov04) / num_samples

top3_success_ratio_cov06 = sum(top3_success_cov06) / num_samples
top4_success_ratio_cov06 = sum(top4_success_cov06) / num_samples
top5_success_ratio_cov06 = sum(top5_success_cov06) / num_samples
```

### 4.4 voxel 指标

voxel 级指标继续保留：

```text
voxel_precision
voxel_recall
voxel_f1
voxel_iou
voxel_dice
```

是否保留 per-sample average voxel 指标可以沿用现有实现。核心变更集中在 instance 和 top-K。

## 5. 实施顺序

推荐实施顺序：

1. 修改 `voxel_evaluator.py`，实现 overlap helper、global instance matching、top-K successful ratio 的底层计算。
2. 修改 `voxel_tuning.py` 的单样本评估和汇总逻辑，让新指标进入 `best_summary.json` 和 `per_sample_best_metrics.json`。
3. 修改 `two_stage_basic.py`，让它执行固定的 `protein_40 Stage 1 -> protein_40 Stage 2 -> protein_110 fixed test` 流程。
4. 轻量验证一个已有深度学习缓存目录，确认不重跑 forward 也能输出新指标。
5. 增加非深度学习 baseline cache 生成过渡脚本。
6. 对六组 baseline 在 `stardard/strict` 两个系统上跑同样的 40 校准 + 110 测试流程。

## 6. 最小验证清单

每次代码改动后至少检查：

```text
1. 现有深度学习 .npz cache 能被读取。
2. protein_40 Stage 1 能只扫 threshold 并输出 best_params.json。
3. protein_40 Stage 2 能读取 Stage 1 best threshold，并在 ±0.10 内搜索。
4. protein_110 阶段 search_space 为空时能固定评估并输出已有惯例文件。
5. best_summary.json 中包含 global_instance_*_cov04/cov06。
6. best_summary.json 中包含 top3/top4/top5_success_ratio_cov04/cov06。
7. baseline cache 与深度学习 cache 能进入同一评估函数。
```

## 7. 暂不做的事

本轮暂不做：

```text
1. 不重写活跃深度学习 YAML 配置。
2. 不另写一套 baseline 后处理或评估逻辑。
3. 不把 protein_110 用于任何参数搜索。
4. 不引入除 threshold 外的后处理参数搜索。
5. 不把 top-K 扩展成 ligand-level recall。
6. 不在 top-K 排序中引入 score_max 或 voxel_count 回退。
```
