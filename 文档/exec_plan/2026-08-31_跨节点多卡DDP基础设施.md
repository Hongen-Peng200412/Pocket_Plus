## 实施结果

- `训练与运行/submit_task.sh` 新增用户参数 `--multi-node-ddp`。只有 GPU 任务且 `--nodes` 大于 1 时允许启用；未显式启用时拒绝多节点申请。
- `训练与运行/runtime/allocation_runner.sh` 在每次 attempt 中只创建一次 release 和 launch，再通过一个 `srun` job step 在每个节点启动一个任务。每个节点任务从 `SLURM_NODEID` 取得节点 rank，并执行同一份冻结的 `run_cmd`。
- `训练与运行/runtime/launch_training_python.sh` 保持单节点 `python -u` 行为；跨节点时使用 static rendezvous 启动 `torch.distributed.run`，每节点训练进程数等于该节点 GPU 数。
- 五个正式训练入口统一经过训练 Python 启动脚本。`unet_c1_no_mainchain.sh` 继续复用 `unet_c1.sh`，因此不需要第二处修改。
- `launch.json` 的 `schema_version` 更新为 2，并新增跨节点开关、实际分布式启动器、Slurm 节点表达式、主节点地址和端口。
- 跨节点 `kill_lock` 先向活动 `srun` 进程组发送 TERM，宽限期后仍未退出才发送 KILL；单节点任务保留原来的立即 KILL 行为。

## 计划与实现差异

- 有益差异：Windows 本地环境无法让两个独立 `torchrun` agent 使用 static rendezvous 完成仿真，因为该环境的 PyTorch 没有 libuv 支持。验收因此拆成“精确核对每节点 agent 命令”和“四个真实 Gloo rank 完成 all-reduce”两项，生产启动方式仍保持服务器历史模板已经采用的 static rendezvous。
- 中性差异：实现同时接入五个正式训练入口，而不是只接入 Find_1。公共辅助脚本使单节点调用保持直接 `python -u`，没有复制第二套训练逻辑。
- 有害差异：无。
- 未完成范围：本轮没有提交服务器任务，因此没有把本地验收表述成真实双节点 NCCL 验收。第一次正式跨节点训练前仍需执行短 smoke，核对 NCCL 初始化、一次优化器更新、rank 0 checkpoint 和远端进程清理。
